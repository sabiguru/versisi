# 1) Comments like Word/PDF highlighting

### The key design rule

**Comments must never silently change the agreement.**
They are **annotations** that can be “resolved” and can *lead to* a new change proposal/version.

### Best implementation (recommended)

Because your “agreement” is structured (sections + feature items), you can support two types of comments:

## A. Feature-level comments (most useful, simplest, disciplined)

Attach comments to a specific **ScopeItem** (feature). This is the core feature.

**Users can:**

* comment on a feature
* reply in a thread
* @mention (optional)
* mark resolved / unresolved
* categorize comment: “clarification”, “concern”, “suggested change”, “question”

**Where it shows:**

* On version pages
* On proposal editor pages
* On client portal version view
* On approval signing page (read-only or allowed, your choice)

**Important rule for discipline:**
On an **approved version**, comments do not modify content; they are just discussion attached to that snapshot.

## B. Highlight/quote comments (optional “Word-like”, but still disciplined)

If you really want “highlight a phrase in a description”, do it as:

* user selects text in a feature description
* you store the **quoted text** + **start/end offsets** (or just quoted text + hash)
* anchor it to the specific `ScopeItem` and field (title/description/criteria)

This gives the “Word highlight” feel without needing a full rich-text document model.

**Caveat:** offsets can break if the text changes during proposal editing.
Solution: anchor comments to:

* the proposal version snapshot at the time of comment
* and show “context changed” if the underlying text changed

### Comment lifecycle (recommended)

* Open → Replied → Resolved
* Resolved can be reopened
* Every comment has: author, timestamp, side (Dev/Client), visibility

### Visibility options

* **Shared** (both sides see)
* **Internal-only** (dev side only) — very useful for agencies
  (Do not add “client-only”; it becomes political.)

# 2) Export formats (Word/PDF/Excel)

## PDF export

✅ Absolutely. This should be first-class.

Exports to include:

* Agreement snapshot (full scope)
* Change summary vs previous version
* Approval signatures metadata
* Audit footer with generation time + version hash

## Word export (DOCX)

✅ Yes, doable and useful for stakeholders who live in Word.

Implementation approach:

* Generate DOCX from a template using a server library
* Keep it simple: headings + tables
* Include signature block at the end

**Rule:** DOCX is an export artifact; editing the DOCX does not change the system record.

## Excel export

✅ Yes, but it should be structured.

Two useful exports:

1. **CSV/XLSX of scope items**

   * columns: version, section, feature title, description, acceptance criteria, priority, status (in/out), comment count
2. **Change log export**

   * columns: version from/to, change type (add/remove/modify), item, summary, rationale

This is very useful for procurement/PMOs without turning your product into Excel.

# 3) Who can create projects and invite people?

Your proposed journey is solid. Here’s a refined model that stays simple but enforces “leaders on both sides”.

## Key concept: two “parties”

Every project has:

* **Dev Party** (the builders: agency/team/freelancer)
* **Client Party** (the buyer/stakeholder group)

Even if it’s one person on either side, the model holds.

---

# Roles & permissions (clean)

## Workspace roles (internal SaaS)

* **Workspace Owner**: billing + settings + can create projects
* **Workspace Admin**: can create projects and manage members
* **Workspace Member**: can be added to projects; optional ability to create projects

## Project roles (per project, per party)

For each party, assign:

* **Leader** (can sign/approve, can invite their party members)
* **Member** (can comment, can propose changes if allowed)
* **Viewer** (read-only)

### Do you allow more than one leader?

**Yes.** Allow multiple leaders per side (common in reality), but enforce:

* at least **1 Dev Leader**
* at least **1 Client Leader**

### How many signatures are required to approve?

Make this a project setting with sensible defaults:

* Default: **1 signature from Client side required**
* Optional: require **1 Dev signature too** (strongly recommended for neutrality)
* Optional: “any 1 leader” vs “all leaders” vs “N of M leaders”

**Recommended default:**

* Client: 1 of N leaders
* Dev: optional 1 of N leaders (on by default for “mutual signoff” positioning)

# Onboarding + project creation journey (updated)

You want: “anyone can register → create project → guided questions.” Great.

## Step 0: Sign up

User enters email/password (or magic link).

On first login, they choose:

* “I’m primarily a **Developer/Agency**”
* “I’m primarily a **Client/Stakeholder**”

This sets initial defaults and copy language — not permissions.

---

## Project creation wizard (exhaustive flow)

### Step 1: Create Project

* Project name
* Short project summary (client-facing)
* Optional: currency/timezone

### Step 2: Choose your role in this project

Ask:

1. Are you on the **Dev side** or **Client side** for this project?

   * Dev
   * Client

2. Are you a **Leader** for your side?

   * Yes / No

If they say “No”, they can still create the project, but they must assign a leader.

### Step 3: Create/Select the other party

If creator is Dev:

* Create/select Client org (name)
* Invite at least one Client Leader email (required to proceed to signoff later)

If creator is Client:

* Create/select Dev org
* Invite at least one Dev Leader email

### Step 4: Invite additional participants (optional)

Two sections:

* Dev team emails (role selector: Leader/Member/Viewer)
* Client emails (role selector)

Rules:

* You can invite multiple people now or skip and invite later
* But the system warns: “You must have at least one leader on each side before approvals.”

### Step 5: Approval model (defaults)

* Require approval for each scope version? (default yes)
* Who must approve?

  * Client: 1 leader (default)
  * Dev: 1 leader (default ON)
* Allow members to propose changes? (default: Dev members yes, Client members no)
* Allow commenting during approval review? (default yes)

### Step 6: Build initial agreement (v1.0) — guided builder

You have two options:

**Option A (fastest): “Feature list” builder**

* Add sections (e.g., “MVP”, “Admin”, “Integrations”)
* Add features per section
* Each feature has:

  * Title
  * Description
  * Acceptance criteria (optional)
  * Priority (Must/Should/Could)

**Option B: import**

* paste text and auto-split into bullets (optional)
* upload CSV (Phase 2)

### Step 7: Review & send for approval

Show:

* Full v1.0 snapshot
* Diff summary (none)
* Approval recipients (leaders)
* Send button

### Step 8: Client portal experience

Invited leaders get magic link:

* View v1.0
* Comment for clarification
* Approve / Decline

Once approved:

* v1.0 becomes immutable
* project status becomes “Active”

# Data model additions (for Claude)

## Comments (minimal but powerful)

* `CommentThread`

  * id
  * projectId
  * entityType: PROPOSAL_ITEM | VERSION_ITEM
  * entityId (proposalItemId or scopeItemId)
  * field: TITLE | DESCRIPTION | ACCEPTANCE (optional)
  * quotedText (optional)
  * anchorMeta (jsonb: offsets/hash)
  * visibility: SHARED | INTERNAL
  * status: OPEN | RESOLVED
  * createdBy (user/clientUser)
  * createdAt
  * resolvedAt, resolvedBy

* `CommentMessage`

  * id
  * threadId
  * body
  * createdBy
  * createdAt

This gives Word-like discussion without turning into a full doc editor.

# Product discipline: how comments interact with versions

**Rule:** Comments are not changes.
Changes require a **new proposal** → approval → new version.

How the UX should guide this:

* In a comment thread, add a button:

  * “Convert to change proposal item” (for dev leaders)
  * This pre-fills a proposal change note referencing the comment

That keeps the system clean.
