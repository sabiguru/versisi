# BUILD BRIEF — “Versioned Scope Agreement” SaaS

## 0) One-sentence product definition

A system-of-record where **devs and clients agree on a project scope**, then every change becomes a **new version** (Git-like commit history) with **threaded comments** and **explicit sign-off**, and the full history can be exported (PDF/DOCX/XLSX).

## 2) Core Concepts (Non-negotiable Discipline Rules)

1. **Approved versions are immutable.**
2. All changes happen via **Change Proposals**, which produce the next **Scope Version** upon approval.
3. **Comments do not alter scope.** They are annotations attached to a specific feature item (and optionally to highlighted quoted text).
4. Approvals are explicit, logged, and produce a signature record with IP + user-agent + timestamp.
5. Maintain an append-only **Audit Log**.

---

## 3) Roles & Permissions

### Parties

Every project has two parties:

* DEV party
* CLIENT party

### Project roles (per party)

* `LEADER` — can approve/sign, invite members in their party, submit proposals (config)
* `MEMBER` — can comment; dev members can draft proposals (default yes)
* `VIEWER` — read-only

### Required constraints

* Project must have **at least 1 DEV leader** and **at least 1 CLIENT leader** before any approval request can be sent.
* Default approval rule: **1 of N leaders** on CLIENT side required; **1 of N** on DEV side required (mutual sign-off default ON, but configurable).

### Who can create a project?

* Any registered user can create a project.
* During project creation wizard, user declares they are on DEV or CLIENT side for this project; they may or may not be a leader.
* If they are not a leader, they must invite/assign a leader for their side.

## 5) State Machines & Business Logic

### Project status transitions

* `DRAFT` → `ACTIVE` when v1.0 is approved
* `ACTIVE` → `RELEASED` manual action
* `ACTIVE/RELEASED` → `ARCHIVED` manual action

### Proposal status transitions

* `DRAFT` → `INTERNAL_REVIEW` (optional)
* `DRAFT/INTERNAL_REVIEW` → `AWAITING_APPROVAL` when approval request is sent
* `AWAITING_APPROVAL` → `APPROVED` when required signatures collected
* `AWAITING_APPROVAL` → `REJECTED` if any required leader declines (config)
* `DRAFT/INTERNAL_REVIEW/AWAITING_APPROVAL` → `WITHDRAWN` by dev leader

### Approval status transitions

* `PENDING` (created) → `VIEWED` per recipient events
* `PENDING/VIEWED` → `SIGNED` when recipient signs
* `PENDING/VIEWED` → `DECLINED` when recipient declines
* `PENDING/VIEWED` → `CANCELLED` by internal dev leader/admin
* `PENDING/VIEWED` → `EXPIRED` by due date job

### Creating a new version after approval

When proposal hits `APPROVED`:

1. Generate a `ScopeVersion` snapshot from the proposal sections/items.
2. Set `approvedAt`, set `project.currentScopeVersionId` to this version.
3. If project status is `DRAFT`, set to `ACTIVE`.
4. Mark previous current version as superseded (optional: just implied by `currentScopeVersionId`).
5. Write audit events.

### Diff generation

Compute diff between `baseScopeVersion` and `proposal snapshot` using `sourceScopeItemId/sourceScopeSectionId` mapping:

* Added: proposal items with null source
* Removed: base items absent from proposal
* Modified: same source id with changed fields
* Moved: order/section change

Persist to `ProposalDiffEntry` on save/submit.

## 11) Security & Integrity Requirements

* All portal links must use signed tokens with expiry.
* Signing must verify recipient token matches an ApprovalRecipient and status is pending/viewed.
* On signing, store `ipAddress`, `userAgent`.
* Create `signatureHash` from a canonical JSON snapshot of the agreement + recipient metadata.
* Approved scope versions must be immutable (enforce by only writing them once, no update routes).
* Audit log must be append-only (no delete/update).
